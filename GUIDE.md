## Installing: the details

### macOS

rongo is for Macs with Apple silicon. It is not notarized by Apple, so macOS blocks its first launch, after an update too (a new version is a new app to macOS). Pressing Open Anyway in System Settings → Privacy & Security, or running `xattr -dr com.apple.quarantine /Applications/rongo.app`, takes away the "downloaded from the internet" mark. Do this only for a rongo you got from this repository's releases or its Homebrew tap.

`brew update` before `brew upgrade --cask rongo` matters: Homebrew refreshes a tap at most once a day on its own and says nothing when that fails, so `brew upgrade` alone may not see a release yet.

### Windows

For Windows 10 and 11 on a 64-bit PC. The installer needs no administrator rights: it installs for your account only, into `%LOCALAPPDATA%\Programs\rongo`, and adds rongo to the Start menu. It is not signed, so SmartScreen says it protected your PC the first time (**More info**, then **Run anyway**).

A new installer installs over the old version, keeps your connections and settings, and asks you to close rongo first if it is open (close it, then press Retry).

To uninstall, use Windows Settings → Apps (Installed apps on Windows 11, Apps & features on Windows 10). The uninstaller keeps your data unless you tick **Remove my data (connections, settings, master-password vault, Collection History)**; ticked, it deletes the three folders in the table below (they sit under two top folders, `%APPDATA%\rongo` and `%LOCALAPPDATA%\rongo`). A silent uninstall (`/S`) always keeps it.

## Where rongo keeps things

On macOS, `~/Library/Application Support/dev.rongo.rongo` holds `profiles.json`, `settings.json`, the vault, and Collection History in `history/`; `~/Library/Application Support/rongo` holds the window's size and position. `brew uninstall --zap --cask rongo` deletes both.

On Windows:

| Path | Holds |
|---|---|
| `%APPDATA%\rongo\rongo\config` | `profiles.json`, `settings.json` and the vault |
| `%LOCALAPPDATA%\rongo\rongo\data\history` | Collection History (kept off the roaming profile) |
| `%APPDATA%\rongo\data` | the window's size and position |

The vault, `profiles.json` and an Export Connection file that holds a password are readable only by you (a Windows file permission), except on FAT, FAT32 and exFAT drives, which keep no permissions.

## Build from source

```sh
cargo run --release -p rongo            # normal start
cargo run --release -p rongo -- --mock  # in-memory demo server, no MongoDB needed
./scripts/bundle-macos.sh               # builds target/rongo.app
./scripts/make-dmg.sh                   # builds target/rongo-<version>-<arch>.dmg to hand out
./scripts/bundle-windows.sh             # builds target/rongo-<version>-x64-setup.exe (a Mac cross-builds it)
```

The disk image holds the app, an Applications shortcut to drag it onto, and install notes in Thai. The app is not notarized, so the first launch on another Mac needs System Settings → Privacy & Security → Open Anyway (the notes explain this). The build is for Apple silicon only.

The app icon comes from `assets/icon-1024.png`, drawn by `scripts/make-icon.py`. Re-run that script after changing the design, then run the bundle script again. Only the bundle scripts build with the green leaf (they set `RONGO_RELEASE=1`); any other build, such as `cargo run`, shows the leaf in orange in the Dock and taskbar, so it is never taken for the installed rongo.

The toolchain is pinned to Rust 1.95 in `rust-toolchain.toml`; rustup installs it on first build.

### Building the Windows installer on a Mac

Once: `rustup target add x86_64-pc-windows-gnu` and `brew install mingw-w64 nsis`. Then `./scripts/bundle-windows.sh` cross-builds `rongo.exe` (with the icon and version info), wraps it with NSIS (`scripts/windows/rongo.nsi`) and prints the path of `target/rongo-<version>-x64-setup.exe`. `./scripts/release.sh` builds it too, next to the disk image. The icon, `assets/icon.ico`, is drawn by `scripts/make-icon.py` with the others, so a build never needs Python.

## Features

- **Connections**: host/port lists or `mongodb://` / `mongodb+srv://` URIs, username/password (SCRAM), TLS (CA file, client certificate, allow-invalid), replica sets, and SSH tunnels (password or private key). Profiles are saved in `~/Library/Application Support/dev.rongo.rongo/profiles.json` (on Windows, see [Where rongo keeps things](#where-rongo-keeps-things)), readable only by you. Passwords go into the encrypted vault (see Master password below), never into that file. A password in a pasted URI is moved into the vault when you save. Turning off username/password authentication or the SSH tunnel and saving deletes that saved password from the vault (a password typed while it is off isn't kept). Two rongo windows can save connections at the same time: each change (save, delete, reorder, colour) is made to `profiles.json` as it is on disk then, one window at a time (`profiles.lock` beside it), so neither drops the other's: a colour or lock changes only that, a connection deleted in one window doesn't come back when the other recolours or locks it (it says so), and a lock saved in one window is lifted in the other only through **Allow Writes**. The Connection Manager reads the list again each time it opens (and, if `profiles.json` couldn't be read at launch, tries again, so a file fixed meanwhile is picked up). A save that fails changes nothing, and a `profiles.json` that can't be read is never written over. In the Connection Manager, tick several connections (or ⌘-/⇧-click them; the header box picks them all) and press Connect to open them all at once.
- **Read-only lock**: tick *Read-only (refuse every write)* in the Edit connection form, or right-click a connection → **Make Read-only**. The core then refuses every write on it (inserts, updates, deletes, drops, index and validator changes, imports, and writes from IntelliShell scripts) with a "read-only" error, so the lock holds even for a script that tries to get round the UI. The tree, the breadcrumb and the connection's tabs show a lock icon; the write items in the tree menus and the Insert/Edit/Delete buttons, Index Manager buttons and Import are greyed out, with "Read-only connection" on hover. Reading, exporting and refreshing still work. The lock is saved with the connection, so it is on again the next time you connect; lifting it (**Allow Writes…** in the connection's right-click menu, or clearing the box in the Edit connection form and saving) asks for confirmation first, naming the connection; until you confirm, the lock stays on.
- **Order and colour**: drag a connection in the tree or in the Connection Manager to move it; the Connect menu uses the same order. Give a connection a colour (right-click → Color in the tree, the Color button on its row in the Connection Manager, or the Edit connection form) to tell production from SIT: the colour tints its row in the tree, runs along the top of its tabs, and labels the breadcrumb above the shell and results. The Connection Manager draws each row the same way as the tree.
- **Export Connection**: right-click a connection (in the tree or in the Connection Manager), or pick one in the Connection Manager and press **Export…**, to get it as one `mongodb://` string to give to someone, who pastes it into New Connection (URI) in rongo or Studio 3T. It carries the hosts, replica set, direct connection, default database, auth database and mechanism, and TLS on / allow invalid certificates. **Include username** is ticked; **Include password** is not, and ticking it reads the password from the vault and warns that it travels as readable text. Without the username the string has no auth options either (drivers refuse an auth database without a user). SSH tunnel settings and TLS certificate files (from the TLS tab or named in a URI) are not included, and the dialog says so; nor is a key file's password or an AWS session token typed into a URI, so the only secret the string can carry is the password you tick. **Copy** puts the string on the clipboard; **Save to File…** writes it to a text file, readable only by you when it holds a password; the file is written whole beside the target and renamed over it (a symlink there is replaced, not followed), so a save that fails leaves what was there as it was. One connection at a time.
- **Tree**: connection → replica set members → databases → collections → indexes. Each level loads when you open it. Search with ⌘F (with a match-case toggle). The right-click menus:
  - **Collection**: Open IntelliShell, Export Collection…, Import Data…, Copy Name (⌥⌘C), Copy Collection (⌘C), Rename, Duplicate (a new collection with the same options, such as validator, collation, capped size or time series settings, then the documents and indexes; the documents travel through rongo in batches with their progress in the corner or the Operations panel, and a duplicate that fails or is stopped (⊗) part way is dropped again, or its error says the partial copy remains if that drop fails too, and the tree lists it; a view can't be duplicated), Clear, Drop, Collection History, Add Index…, Add/Edit Validator…, Collection Statistics, Server Info ›, Refresh, Disconnect / Disconnect Others / Disconnect All. Rename and Drop close the collection's tab and Index Manager once the server has done it; a refused one leaves them open, query and page as they were. Add Collection, Rename and Duplicate wait for a name that isn't blank.
  - **Database**: Add Collection, Import Data, Copy All Collections (greyed out until the database's collections are loaded; `system.*` collections are left out), Paste Collection(s)… (⌘V), Database Statistics, Server Info ›, Drop Database (type the name to confirm).
  - **Connection**: Open IntelliShell, Server Info ›, Color, Make Read-only / Allow Writes…, Export Connection…, Paste as New Database…, Refresh, Disconnect / Disconnect Others / Disconnect All.
  - **Index**: Open Index Manager, Copy Keys, Drop Index.
  - **Hover a collection** for a card with Count, Size, Storage Size, Indexes, Total Index Size and when the numbers were fetched, plus a Refresh link.
- **Copy and paste collections**: right-click a collection → **Copy Collection** (or select it and press ⌘C with the pointer over the tree), or a database → **Copy All Collections**; then right-click a database on any open connection → **Paste Collection(s)…** (⌘V with a database selected), or a connection → **Paste as New Database…**, which asks for the new database's name (under 64 bytes, none of `/ \ . " $` or a space). The Paste dialog lists each collection, one line each, with an editable name in the target (spaces around a name don't count); a long source name is cut short (whole on hover), and a line wider than the dialog scrolls sideways. When that name is already taken in the target database, choose **Append** (skip, overwrite or stop at an existing `_id`) or **Replace**; Replace drops what is there first and asks you to type the collection's name (or the database's, for several) to confirm; changing which rows replace clears what was typed. Paste stays off until rongo has listed what the target database holds, and says why if that listing fails. **Rename to …_copy** picks a free name. Copy indexes and Copy collection options and validator are on by default. The documents stream through rongo in batches of 1,000 (read from one connection, written to the other), so a large collection never sits in memory, and the bottom-left activity shows progress; its ⊗ stops the copy between batches and the toast then says how much arrived. Pasting a collection into itself, appending to a time-series collection, appending to or from a view, pasting a view over the collection it reads from, and replacing a collection whose uuid can't be read are refused, and so is writing into a collection that the same paste copies from: by name on one connection, and by the collection's uuid when two connections reach the same server (a view has no uuid, so there only its name on one connection tells; its definition is read before anything is written, so a replaced view is still copied as it was). The toast afterwards reads like "Pasted 1 collection into Mock B · copy: 8 documents", with skipped and overwritten counts and any collection that failed. Paste is greyed out on a read-only connection and when nothing is copied. What you copy lives in rongo, not on the system clipboard; the collection names are also put there as text so that ⌘V reaches the tree.
- **Add Index**: an index name (empty means MongoDB's default name, e.g. `chatID_1_sentAt_-1`) and five tabs. **Fields**: the fields in order, picked from the collection's sampled fields, each 1, -1, text, 2dsphere, 2d or hashed. **Options**: Unique, Sparse, Hidden, TTL with expiry seconds, and Partial with a filter. **Text options**: default language, language override field, weights. **Geo options**: 2dsphere version, 2d bits, min and max. **Collation**: locale, strength, case first, case level, numeric ordering. At the bottom: Create in background, and a JSON preview of exactly what will be sent. The definition goes to `createIndexes` unchanged, so every option reaches the server. When an identical index is already there the server builds nothing, and the toast says so ("Index email_1 already exists; nothing was created"), never "Created index". The Index Manager's View details and Edit index are this form filled from an index, and its **Add as New Index…** opens it filled from one with no name (below).
- **Index Manager** (click **Indexes (n)** under a collection, or Manage Indexes…): Name (expand to see keys and options), Type (Regular, Text, 2dsphere, Hashed, Wildcard), Properties (Compound, Unique, Sparse, TTL, Partial, Hidden), Size, and Usage from `$indexStats`. Toolbar: Refresh, Add, Drop, Edit, View details (also in a row's right-click menu), Hide/Unhide. The footer shows the index count and total size.
  - **View details** and **Edit index** open the Add Index form filled from the index: its name, its keys in order (a text index shows its text fields, with their weights on Text options), and its options, text, geo and collation settings. View details changes nothing: every field is greyed out (the tabs still switch), OK stays off, Cancel, Esc or a click outside closes it, and JSON shows the index as the server lists it. It works on a read-only connection too.
  - **Edit index** changes only an index's TTL (its expire-after seconds, for a TTL index) and Hidden (not for `_id_`). Everything else is greyed out, and its hover points to Add as New Index…. OK sends `collMod` with only what you changed, and stays off until something has; JSON shows that command. A change, typed or ticked, keeps the dialog open on Esc or a click outside.
  - **Add as New Index…** (in both) closes the dialog and opens Add Index filled from the index with the name left empty, so MongoDB names the new index unless you type a name. Change the keys, uniqueness or anything else, create it, then drop the old index yourself: rongo never drops an index here.
    - When the old index has MongoDB's default name (`email_1`) and the keys are unchanged, the new one would get that same name, so Create index waits until you type a name or change the keys, and says why.
    - While the keys, collation and partial filter are still the old index's, a note says that MongoDB keeps one index per key pattern unless the collation or partial filter differ. Changing only options such as Unique or Sparse therefore needs the old index dropped first, and rongo doesn't do that for you; the server refuses the new index and nothing is created.
    - A collation's fields the form has no place for (`alternate`, `maxVariable`, `normalization`, `backwards`, e.g. Thai's `alternate: "shifted"`) go along as listed while the locale stays the same; the Collation tab shows them. Change the locale and they are left out, and the tab says so, since they were set for the old one.
    - It says what of the old index it doesn't carry over: fields the form has no place for (such as `wildcardProjection`) and those the server sets itself (`v`, `textIndexVersion`, a collation's `version`).
    - Greyed out on a read-only connection.
  - **Server Info ›**: Server Status, Build Info, Host Info, Replica Set Status, Current Operations, Connection Status. Each opens in its own tab.
- **Tabs**: ✕, a middle-click or ⌘W closes a tab. Right-click a tab for Close, Close Others, Close Tabs to the Right, Close Tabs of its connection, and Close All. A tab whose script is running stays open. When the tabs closing include IntelliShell tabs with a script in them, rongo asks first, since a script closes with its tab. ▾ at the end of the bar lists every tab when they don't fit.
- **Collection tab**: Query / Projection / Sort / Skip fields in shell syntax, pages of 20 to 1000 documents (or any size up to 50,000 typed in), and Count Documents (an estimate when there is no filter, otherwise an exact count). Last page counts the documents first if they have not been counted yet, then jumps to the end.
- **Views**: Table view has a type icon and type colour in each cell. Drilling works as in Studio 3T: double-click an object or array cell (or select it and press ↩, or right-click → Step Into Column) to step into that column for every document on the page. An object's fields become the columns; an array's elements become columns 0, 1, … up to the longest array, a shorter array's cells left empty, and an element that is itself an object or array can be stepped into the same way (its paths are `gameType.0`, `items.2.name`, which Edit Value, Copy Field Path and the header sort use). Every drilled level starts with a **{Document id}** column, each row's document `_id`; it stays first and can't be moved, hidden or sorted by. Step Into Cell (⇧↩) shows just that row's value instead: an array's elements as rows (`gameType [row 5]`), an object as one row (`gameName (row 5)`). The breadcrumb above the table follows the selected cell as Studio 3T's does (`games > gameName`, then `games > gameName > en` once stepped in and `en` clicked); earlier parts step back out, and Esc steps out one level. A drill into one row's value stays with that document when the page is fetched again or sorted (the breadcrumb shows its row), and steps back out when the document is no longer on the page. Only the columns in view are laid out, so an array of thousands of elements stepped into scrolls as smoothly as a few. Tree view shows Key, Value and Type columns. JSON view shows the documents in shell syntax, with a find bar: press ⌘F with the pointer over the results (it switches to the JSON view; ⌘F again selects what you typed), type, then ↩ / ⇧↩ for the next / previous match and Esc to close. Matches are highlighted, the counter shows "n of m", and **Aa** matches case. The search runs in the background, so typing stays smooth on a 50,000-document page.
- **Column headers sort**: click a header for ascending, again for descending, a third time for the order the rows arrived in. The rows on screen are sorted in place, instantly: a query's current page as it stands (each page as you turn to it), with nothing sent to the server. To sort the whole collection, use the Sort field or the column menu's Sort Collection Ascending/Descending, which re-run the query.
- **Column order**: drag a column header left or right to move the column; a blue line shows where it will land, and it keeps its width. The order stays for the next pages of that result. Inside a drill into one row's value, column order and hidden columns go by the field path, so the same field in another row shares them. Right-click → Column › Reset Column Order puts it back.
- **Selecting rows**: click a row, ⌘-click to add or remove one, ⇧-click for a range, or drag a dashed box from a row or from the empty space under the rows: every row it touches is selected (⌘-drag adds them to the selection). Dragging past the top or bottom of the table scrolls it, and the box follows. Right-click, ⌘C (Copy Document(s)), Update, Delete and Export then act on all the selected documents; the field shortcuts (⌘U fills in the clicked cell), ↩ / ⇧↩ and the menu under the rows act on the selected row you last clicked or ⌘-clicked; a ⇧-click range keeps the row it started from (click row 2, ⇧-click row 7: they act on row 2). A page turn or a step into a value clears the selection, and the next ⇧-click starts a new range.
- **Result table right-click menu**: Field › (Edit Value, Set to null, Remove Field), Document › (Insert, Delete, View JSON, Edit JSON, Clone), Column › (Sort Collection Ascending/Descending on a query, which re-runs it sorted and fills the Sort field; Sort Ascending/Descending on other results; Hide, Show All: hidden columns are kept per drill level, so stepping back out shows that level as you left it), Copy › (Value, Field Path, Document(s), _id, and Selected as CSV / for Excel, each with or without a header row: the selected rows in the columns the table shows, hidden columns left out and, when drilled in, {Document id} first, ready to paste into a spreadsheet), Paste Document(s), Step Into Column/Cell, Refresh View/Document, Update Dialog, Delete Dialog, Export Documents. After saving a document in the editor, Edit Value, Set to null or Remove Field, the view re-reads just that document (with the query's projection): the rest of the page, the selection and the scroll position stay. While a page is still on its way, or if the server won't read the document on its own, the page is fetched again instead. Inserts, deletes, Paste and the Update/Delete dialogs fetch the page again. Right-click the empty space under the rows for the menu of that row (see Selecting rows), or, with nothing selected, Insert, Paste, Refresh View, Update/Delete Dialog and Export.
- **Paste to import**: copy documents from anywhere (rongo, Studio 3T, mongosh output, JSON, mongoexport lines, Extended JSON), click into a collection's results, and press ⌘V. rongo asks "Import N documents from the clipboard?" and can strip `_id`s so the documents insert as new ones. Documents copied in rongo (⌘C, Copy Document(s), the JSON view's ⌘A ⌘C) paste back with the same types: a whole-number double is copied as `Double(5)` and stays a double (the views show it as `5.0`). Plain JSON (mongoexport lines, a JSON array, Extended JSON) is read as written, without the JavaScript engine: keys stay in their order, `5.0` is a double and `5` an integer, integers above 2^53 stay exact (as Int64), and every Extended JSON type (`$timestamp`, `$minKey`, `$uuid`, …) is read. Anything else is read as shell syntax, all in one go: text between or after the documents that isn't a document is an error rather than dropped, and reading gives up after 2 seconds (paste fewer documents at a time).
- **Export / Import**: JSON lines (mongoexport style), JSON array, or CSV, for the whole collection or the current query. Import detects the format from the file. CSV numbers and booleans become typed values, and dotted headers become nested fields. Import inserts every document that can go in: one whose `_id` is already in the collection is skipped, one the server refuses for another reason (a validator, say) doesn't stop the rest, and the toast says how many were inserted, skipped and refused, with the first reason. When the server applies a batch but can't confirm it as its write concern asks (a write-concern error, replication timing out, say), the import goes on and the toast says the write was not confirmed, counting those documents apart from the confirmed ones. It inserts as it reads, a batch of 1,000 at a time with its progress in the corner or the Operations panel (⊗ stops it between batches), so a file found malformed part way leaves the batches before it inserted, and the message says how many; the tree and the collection's open tab then show them, as after a finished import. An export is written to a new `.part` file beside the file (never one already there) and takes the file's place only when complete, with that file's permissions, so a failed or stopped export leaves a file already there as it was. Exporting to a symlink replaces the file it points to and keeps the link.
- **Update / Delete dialogs**: select documents, then right-click → Update Dialog… (⌘U) or Delete Dialog… (F8). The **Query** tab starts with `{ _id: { $in: [ … ] } }` for the selection and can be edited, or filled from *Apply predefined query* (Selected Document(s), Current Query, All Documents). The **Update** tab starts with `$set` of the cell you clicked, its type kept (e.g. `NumberLong(…)`), and supports a simple update document or an aggregation pipeline. Upsert and Multi checkboxes, and Validate JSON. An empty query with Multi on needs an extra confirmation.
- **Running work**: a query, count or document refresh that takes more than a moment shows in the result's status line (next to Count Documents) with a moving bar and the time taken; ⊗ discards it and keeps the rows on screen. Other work (connecting, loading the tree, writes, scripts in other tabs) floats in the bottom-left corner only while it runs, with its connection's name (a paste names both, as in "SIT → UAT"); while the sidebar is open, the corner floats just above the Operations panel under the tree (its header, while folded), and while the panel is unfolded the corner leaves out the writes and data moves the panel lists and still shows the rest; ⊗ discards a read, and stops a copy, duplicate, import, export, recorded delete or update, or restore between batches (the toast then says what was done). A write the server finishes once it has begun (clear, drop, rename, create or drop an index, insert, a delete or update without history, a command that isn't a read) has no ⊗: stopping it in rongo would leave the server carrying on unseen, so it runs to the end and its toast says what it did. **+n more** lists the rest. Closing a tab cancels what it was still waiting for: its results' queries and counts, an Index Manager's details, a Collection History tab's conflict check or Show changes (a restore already sent goes on).
- **Operations panel**: **▸ Operations** under the tree (with "· N running" while something runs) unfolds a list of the writes and data moves sent this session: pastes, Duplicate, Import, Export, Update / Delete (the dialogs and the table), Restore, Clear, Drop, Rename, index and validator changes, and single documents inserted, saved or deleted. Reads (queries, counts, the tree), connecting and IntelliShell scripts are not listed. Running entries come first, then finished ones, newest first in each. An entry shows what it is, when it started (in the Settings time zone) and how long it ran, its connection in the connection's colour (a paste names both ends, "SIT → UAT"), its progress while it runs, with ⊗ where the corner has one, and once it has finished ✓ (done), ⚠ (done with something to know: documents skipped or refused, a write not confirmed, a history warning, a collection of a paste that failed), ✗ (failed) or ⊘ (stopped by you, with ⊗ or a Cancel button; a stop caused by a problem, such as Collection History reaching its size limit or the connection switched to read-only, is ⚠, or ✗ when nothing was written), with the whole of what its toast said, never cut short. A paste of several collections has a line for each: waiting, running with its count, ended with its count (a plain circle: how it went shows once the paste is done), then done with its documents (and those skipped or overwritten) and how long it took, its error, stopped part way, or not copied when the paste was stopped before it. Only the rows in view are laid out, so a long list or a paste of hundreds of collections costs a frame what is on screen. Right-click an entry for **Copy** (the entry as text), **Reveal in Finder** (**Show in Explorer** on Windows) for an export's file, and **Remove** once it has finished; the eraser on the header clears every finished entry. Drag the line above the header to make the panel taller (up to 70% of the sidebar). The list is kept for the session only, at most 200 entries (then the oldest finished one goes), and never saved. A write refused before it began because its Collection History would not fit leaves no entry; going on without history adds its own.
- **Languages**: text in any script the system (macOS or Windows) has a font for shows as text, not boxes: Thai, Chinese, Japanese, Korean, Lao, Khmer, Myanmar, Vietnamese, and more through Arial Unicode. rongo uses the system's own font files (macOS's, or on Windows the fonts in `%WINDIR%\Fonts`; memory-mapped, so a 50 MB CJK font costs only the glyphs drawn).
- **Editing**: add, edit, clone and delete documents (deleting asks for confirmation). The editor uses shell syntax and keeps BSON types: `ObjectId("…")`, `ISODate("…")`, `NumberLong("…")`, `NumberDecimal("…")`, `Double(5)`, and for the old types `BSONSymbol("…")` and `DBPointer("db.coll", ObjectId("…"))`. A regex is shown as `/…/` when JavaScript reads it as written, else as `BSONRegExp("pattern", "options")` (PCRE-only syntax such as `(?i)`, or a pattern JavaScript refuses), so a document holding one still opens. **Find**: press ⌘F in the document editor or in View Document (F3) for the JSON view's find bar above the text: type, then ↩ / ⇧↩ for the next / previous match; every match is highlighted, the current one scrolled into view, the counter shows "n of m", and **Aa** matches case. ⌘F again selects what you typed. Editing the document with the bar open finds again as you type. Esc (or ✕) closes the bar, never the dialog. Closed from the bar, it leaves the current match selected in the text, so typing replaces it (in View Document, ⌘C copies it); Esc pressed while typing in the text leaves the caret where it was. With the bar closed, Esc closes the dialog as before. **Undo**: ⌘Z in the text undoes about a word at a time, as in IntelliShell's editor, and puts the caret back where it was; ⇧⌘Z or ⌘Y redoes.
- **Dialogs keep what you typed**: a click outside a dialog, or Esc, closes it only while nothing was typed into it. Once you have typed into the document editor, Update / Delete, Export, Import, Validator, Edit Value, Add Index, Edit Index, Paste or Change Master Password (or changed something in Settings without saving), only its Cancel button closes it, so a stray click can't throw the work away. The Connection Manager's form never closes that way (Cancel goes back to the list).
- **Collection History**: before rongo deletes or changes documents, it saves them as they were, on this computer, as Studio 3T does. Recorded: deleting selected rows, the Delete Documents dialog, saving in the document editor, Edit Value, Set to null and Remove Field, the Update Documents dialog, and Paste → Append → overwrite existing `_id`s (the target documents it replaces, in the target connection's history). Not recorded: IntelliShell scripts, Drop Collection, Clear Collection, Drop Database, Paste with Replace, inserts (including the document an upsert creates), and time series collections. The Update and Delete dialogs have a **Keep the documents in Collection History** box, ticked by default. History is on by default for deletes and updates, keeps 30 days and at most 1 GB (the oldest entries go first), and is trimmed at start-up, when you save new limits in Settings, and after a recorded operation once the history passes its size limit (entries past their age are looked for then at most once an hour); a trim that can't read or remove part of the history goes on with the rest and says what it left; turn it off in Settings, or per connection in the Edit connection form (**Collection History: Use Settings / On / Off**; On records even when Settings turn history off). It is kept in `~/Library/Application Support/dev.rongo.rongo/history/` (on Windows, see [Where rongo keeps things](#where-rongo-keeps-things)), one folder per connection profile, database and collection, one file per operation, readable only by you; each record in it is encrypted (XChaCha20-Poly1305) with a key kept in the vault that holds the passwords. When an operation's history would pass the size limit or the free disk space, rongo asks **Keep no history for this operation?** and goes on only once you type the collection's name (for a paste that overwrites in several collections, the database's name, as the Paste dialog asks for Replace); when another question is open by then, the operation is not sent and a message says so, to try again. That size is an estimate (the matching count times the collection's average document size); rongo checks again before each batch of 1,000, and an operation or restore that outgrows the limit stops there, with what it did kept in history and the reason in its message. A delete, update, restore or paste write the server did not confirm (the connection dropped, a write of many documents failed part way, or the server applied it but reported a write-concern error) is said as such, **The server did not confirm this write: it may have been applied. Check before retrying.**, with what was confirmed (documents a restore put back under a write-concern error are counted apart, as not confirmed); the documents as they were stay in history, and the document editor stays open with your edits. A write-concern error on a write kept out of history (an insert, ⌘V Paste Documents, a drop, or a delete or update with history off) is said the same way, and a drop it answers closes the collection's tabs, as the drop happened. Renaming a collection moves its history to the new name, in the background, once the server has renamed it (a refused rename moves nothing; Rename waits while a delete, update or restore on that collection is still being recorded). Dropping a collection or a database keeps its history: open it from **Settings → Collection History**, where restoring a delete recreates the collection. Deleting a saved connection in the Connection Manager asks first and offers **Also delete its Collection History (N MB)**, ticked by default; untick it to keep the history, which Settings then lists under *deleted profile*.
- **Restoring from Collection History**: open a collection in the tree and click **Collection History** under it (or right-click the collection → Collection History). The tab lists what was saved, newest first: when (in the Settings time zone), Delete or Update, how many documents, the size, and **Cancelled** (stopped between batches: it holds what was done up to then), **Incomplete** (the operation failed part way, or the file is damaged), **Restored**, or **Could not be read** (its file could not be read just now, say for its permissions: it can't be restored until it reads, and the tab's Refresh button lists it again). Select an entry to see its first 1,000 documents (fewer when they are large) in the Table view; for an update, **Show changes** puts each saved version beside the document as it is now, a changed field's old value in red and its new one in green. **Restore** (or ↩ while the entry list has the keys: from when the tab opens until you click into the preview, and again after clicking the list) first checks the collection as it is now: a deleted document whose `_id` is back, or an updated one that is gone or was changed again, is a conflict. Then it always asks before writing anything: it names the connection (in its colour) and the collection, says what it will do (e.g. "Insert 2 deleted documents back into shop.orders"), and, when some documents conflict, says how many, shows their first `_id`s and lets you choose **Skip** (the default), **Overwrite** with the saved versions, or, for a delete, **Insert as New** with new `_id`s. Nothing is written until you click **Restore N** (↩ doesn't answer it; Esc cancels). Deleted documents are inserted (which recreates a dropped collection) and updated ones replaced by `_id`. Whatever a restore replaces is kept in a new entry first, so that can be undone the same way; what it inserts is not kept (all of a restored delete, documents inserted with new `_id`s, and an updated document that no longer existed), so those can't be undone from history. Progress and Cancel show in the tab, the toast says what was restored, overwritten or skipped, and the entry is then marked Restored. Restore is off on a read-only connection, and until its connection is open (for a history opened from Settings). The tab's **⋯** menu has Remove from History… and Empty History for This Collection… (which removes them in the background, only the entries recorded before you asked; both wait while a delete, update or restore on that collection is still being recorded). Time series collections and views have no history.
- **IntelliShell**: mongosh-style JavaScript on an embedded QuickJS engine. It supports `db.coll.find/aggregate/insert*/update*/replace*/delete*/countDocuments/distinct/createIndex`, cursors, `use db`, `show dbs`, `show collections`, `print`, and the BSON constructors. A `find()` the script doesn't read opens as a pageable "Find Query (line N)" tab. `aggregate()` output and a final document value open as result tabs too; an unread cursor with `.map()` shows the mapped values. A run opens at most 20 tabs for unread cursors and prints how many more there were. A server error thrown into a script carries its `code` (`if (e.code === 11000)`), and a `codeName` for the common codes (from a table in rongo: the core keeps only the code). Each result tab can be pinned. Stop interrupts loops and server waits. A tab with a running script closes only once it is stopped; Disconnect (also Disconnect Others / All, and Save & Connect on an open connection) stops its connection's running scripts as Stop does, and a toast says how many. Autocomplete opens as you type: collection names and methods after `db.`; inside a query (`find({ l…`), the collection's field names (sampled from 100 documents, nested paths included) followed by every MongoDB query, update and aggregation operator; `ObjectId`, `ISODate`, … in value positions; and `"$field"` references in pipelines. Matches can be anywhere in the name, and the matching part is highlighted. ↑↓ choose, Enter or Tab accepts, Esc closes. **Find**: press ⌘F while typing in the script for the find bar above it, under the toolbar: type, then ↩ / ⇧↩ for the next / previous match; every match is highlighted, the current one scrolled into view, the counter shows "n of m", and **Aa** matches case. ⌘F again selects what you typed. While the script or the bar has the keyboard (a click on the bar leaves it there), ⌘F finds in the script wherever the pointer is; otherwise ⌘F goes by the pointer as elsewhere: the results under it, else the tree. Editing the script with the bar open finds again; Load file and New start over at the new script's first match. Esc in the bar's field, or ✕, closes the bar and leaves the current match selected in the script, so typing replaces it. Esc while typing in the script: with the suggestions open, the first Esc closes them and the next one closes the bar; otherwise Esc closes the bar and leaves the caret where it was. In the script, ⌘↩ / ⇧⌘↩ run as always (the selection or everything / the statement at the caret); from the bar's field, ⌘↩ (or F5) runs the whole script and ⇧⌘↩ the statement holding the current match (the caret's when nothing matches). Each tab keeps its own bar. **Undo**: ⌘Z in the script undoes about a word at a time (a run of spaces and the word after it; ↩, a pause of a second, moving the caret, switching between typing and deleting, a paste and an accepted suggestion each begin a step of their own) and puts the caret back where it was; ⇧⌘Z or ⌘Y redoes. New and Load file can be undone too, with ⌘Z right after them: ⌘Z brings the script before them back with its file (the one it was loaded from or saved to, or none), so ⌘S never saves it over the file just loaded; ⇧⌘Z puts the loaded script back as it was loaded (from memory: the file isn't read again) with its file. Typing over a selection is one step with the rest of the word typed after it, whatever the first character typed, and its undo selects what it replaced again. Each tab keeps its own undo, and ⌘Z in the find bar's field undoes only the field.

### Master password

rongo asks for a master password each time it starts, before anything else can be used. The first launch asks you to set one (at least 8 characters, used exactly as typed, with no trimming); after that the same dialog unlocks. **Quit** is the only way past it without the password, apart from **Forgot?**, which starts a Reset (below) that deletes the saved secrets. Once unlocked, nothing else in rongo asks again until you quit, and there is no auto-lock.

All saved connection and SSH passwords, and the key that encrypts Collection History, live in one encrypted file, `vault`, next to `profiles.json` (Argon2id key derivation, about half a second per try, then XChaCha20-Poly1305). It is readable only by you. `vault.lock` beside it makes two rongo windows take turns writing it, and `vault.reset` appears after a Reset. rongo no longer keeps secrets in the Keychain, so rebuilding or running an unsigned app no longer brings up macOS password prompts. One exception stays outside the vault: a key file's password (`tlsCertificateKeyFilePassword`) or an AWS session token typed into a URI's options is saved as typed in `profiles.json` (Export Connection leaves them out).

- **Moving from the Keychain** (macOS, once): the first launch of this version, when there is no vault yet and your connections have saved passwords or SSH passwords, or Collection History exists (or `profiles.json` can't be read, so its connections might), reads rongo's Keychain items (the last time rongo reads the Keychain; macOS may ask once more when rongo deletes the items afterwards), asks you to set a master password, writes the vault, and only then deletes rongo's Keychain items. Quit during the move changes nothing. If the move fails, the dialog says why and offers **Try Again** (it runs the move again; not when the Collection History key in the Keychain is damaged), **Reset…** and **Quit**. If macOS doesn't let rongo delete its Keychain items after a move that worked, rongo opens all the same and says so once (the vault holds everything; Keychain Access lists the items under dev.rongo.connections).
- **Settings → Master password**: **Change Master Password…** (the current password, then the new one twice) re-seals the same secrets, so Collection History stays readable.
- **Forgot your password?** It can't be recovered. **Forgot?** on the unlock dialog, and **Reset…** in Settings, open the same question: Reset deletes every saved password (the connections stay; type their passwords again), and Collection History can no longer be read. The box **Also delete all Collection History (N MB)** is ticked by default; it deletes only history recorded before the Reset. Unticked, the files stay (Settings lists them, and retention still trims them) but can't be opened. On macOS, Reset also deletes rongo's `vault` item in the Keychain and the per-connection items of the connections still saved, so they can't be moved back. Reset always asks first, and waits (says so, and asks nothing) while a delete, update, paste or restore is still writing Collection History, as Rename does.
- **Two rongo windows**: their writes merge, so one never drops the other's passwords. If the other window changed the password or did a Reset, this window asks to unlock (or set) again before it writes, and closes its Collection History tabs. A connection form you were saving keeps what you typed, with "The vault was changed in another rongo window: unlock again, then Save" (any other failed save also brings the form back, with the reason). Test connection reads the passwords as the other window left them. A delete, update, paste or restore that keeps Collection History checks first too, so nothing is saved under a key the other window's Reset made useless: it does nothing and says "unlock again, then try again" (or, while the other window holds the vault for a moment, that it is busy); the Delete question or the Paste dialog stays open, to go on once unlocked.
- The demo server (`--mock`) goes through the same dialog.

### Settings

Open Settings with the gear button on the toolbar or ⌘,. They are saved in `~/Library/Application Support/dev.rongo.rongo/settings.json` (on Windows, see [Where rongo keeps things](#where-rongo-keeps-things)), written whole each time (a crash can't leave half a file). If that file can't be read (a typo made by hand, say), rongo keeps it as `settings.json.unreadable` (replacing an older one), starts with the default settings, and says so.

- **Double-clicking a collection opens**: IntelliShell with `db.getCollection("…").find({})` already run (the default), or a collection tab with a query bar. The right-click menu offers both either way.
- **Show dates in**: UTC (the default), this computer's time zone, or a fixed offset such as UTC+07:00. The setting applies to tables, the Tree and JSON views, the document editor and shell output. Dates with an offset, such as `ISODate("2026-01-02T10:04:05.000+07:00")`, are still exact instants, so editing a document never shifts its time. Exported files always use UTC.
- **Default page size**: 1 to 50,000 (very large pages make the JSON view slow to lay out). Each result view also takes a typed size (press Enter to apply) or a preset from ▾.
- **Collection History**: on (the default) or off for every connection that doesn't choose for itself; which operations to record (**Deletes**, **Updates**); and **Keep for** N days **and at most** N MB, the oldest entries going first. New limits trim the history as soon as you save (in the background); lower ones ask first, saying roughly what they remove (entries older than the new number of days, about how many MB of the oldest entries). Below them: **Using N MB**, **Clear All History…** (asks first), and every history kept on this computer, with its connection (or *deleted profile*), database, collection, entries and size. **Open** shows it in its Collection History tab, also for a dropped collection or a connection that isn't open (restoring then waits until you connect); it closes Settings, so it waits until unsaved changes are saved or cancelled. **Delete…** removes that collection's history after asking (entries recorded after you asked stay). Delete and Clear All wait while a delete, update or restore is still being recorded. Sizes and the list are read in the background from the files' names and sizes, so a large history never holds up the window. See Collection History under Features.
- **Check for new versions at launch** (on by default): at most once a day, as rongo starts, it asks GitHub for its latest release (`https://api.github.com/repos/yamete-jpy/rongo/releases/latest`) in the background. The request carries rongo's version (in its User-Agent) and nothing about you, your connections or your data; like any web request it reaches GitHub from your IP address. It goes through a proxy only when the `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` environment variables are set (not the system proxy settings); when the check can't get through (offline, blocked, rate-limited), it simply shows nothing (and asks again at the next launch). When that release is newer, a banner under the toolbar says so (once the master password is in), with **Open Download Page** (the release page, in your browser) and **Later** (hides it until a still newer version is out); on macOS it also gives the Homebrew command, `brew update && brew upgrade --cask rongo`, with **Copy** to put it on the clipboard. The newer version is remembered, so the banner shows at every launch, without asking again, until you press Later or run that version or a newer one. rongo never downloads or installs anything itself. Untick the box to turn the check off.
- **Master password** (last section): **Change Master Password…** and **Reset…**, as described under Master password above. Reset closes Settings, so it waits until unsaved changes are saved or cancelled.

Ctrl+Shift+[ and Ctrl+Shift+] switch tabs by the key's position, so they work on the Thai layout and others where those keys type other characters.

## Layout

```
crates/core   no UI: protocol, connections, SSH tunnel, BSON formatting, profiles, mock server
crates/shell  QuickJS runtime, BSON types (src/bson.js), mongosh-style prelude (src/prelude.js), autocomplete
crates/app    egui UI
```

The UI sends `Command`s to the core and gets `Event`s back over channels. MongoDB I/O runs on a small tokio runtime, so the UI thread never blocks on the network. Each shell tab runs scripts on its own thread.

## Limitations

- Through an SSH tunnel, rongo connects directly to the first host. Replica set discovery would hand out member addresses that are only reachable from the far side of the tunnel.
- The SSH host key must already be in `~/.ssh/known_hosts` (on Windows, `%USERPROFILE%\.ssh\known_hosts`). Connect once with `ssh` to add it: on Windows run `ssh user@host` once in PowerShell (Windows 10 and 11 include OpenSSH).
- TLS through an SSH tunnel checks the certificate against `127.0.0.1`, so it fails for certificates issued to the server's name (Atlas, `mongodb+srv://`, DocumentDB) unless "allow invalid certificates" is ticked.
- The tunnel's local port (127.0.0.1, random port) accepts any local process, the same as `ssh -L`. MongoDB authentication still applies to every connection.
- A find result tab is a live query: paging or refreshing it re-runs the query. A document edited so that it no longer matches the query (or under a Sort field that would move it) stays where it is on the page until the next ⌘R, since only that document is read again.
- In the Table view a drilled level's first column is **{Document id}**, each row's document `_id`: a field of the stepped-into values that is itself named `{Document id}` gives way to it there (the Tree and JSON views still show it).
- Edit Value and Set to null on an empty cell of an array's index column (an element that array doesn't have) write that element as MongoDB does: the array is padded with nulls up to it. Where the document has no array there at all, `$set` of `gameType.0` creates an object `{ "0": … }` instead.
- Each shell run starts in a fresh JavaScript context, so variables do not carry over between runs. Only the current database (`use`) is kept.
- The shell accepts and ignores the options that can't change a result: `comment`, `maxTimeMS`, `allowDiskUse` and `writeConcern` on any method, and the cursor methods `comment()`, `maxTimeMS()` and `allowDiskUse()`; `batchSize` applies to `find` and `aggregate` (also as `cursor: { batchSize }`) and is ignored elsewhere.
- Options the shell can't honour and whose loss could change a result throw `not supported: …` rather than being ignored: `hint` (as an option or `cursor.hint()`: it can change which document `updateOne`/`deleteOne` acts on, or what a sparse or partial index returns), `collation`, `arrayFilters`, `let`, `explain`, `bypassDocumentValidation`, `ordered: false` on `insertMany`, `createCollection` options (capped, validators), any other option a method doesn't list (find takes sort/limit/skip/projection/batchSize, countDocuments skip/limit, updates and replaceOne upsert), `sort()`/`limit()`/`skip()`/`projection()` on an aggregation cursor (add the stage to the pipeline instead), and `getCollectionInfos` filters on anything but `name` and `type`.
- Some pasted Extended JSON forms are not read: legacy `$binary` with `$type`, and mongosh 2's `Binary.createFromBase64`.
- A run keeps the first batch of at most 20 unread aggregations (about 64 MB in all) until it ends; any more are let go and run again from their pipeline when the script reads them or they are shown as a tab. A pipeline with `$out` or `$merge` is never run again: it runs once, where the script calls it.
- Top-level `await` is not supported in the shell: put the code in an async function and call it, `(async () => { … })()`. `await` inside it and `.then()` callbacks run once the script's statements have; a promise left as the final value shows what it resolved to, and a rejection nobody handles is the run's error.
- In a script, numbers are JavaScript numbers: a document the script reads and writes back has its whole-number doubles turned into integers. Wrap them with `Double(…)` to keep them doubles.
- The Result tab of a script's final value (`db.c.findOne(…)` as the last line, say) shows JavaScript values, so whole-number doubles show as integers there. Leave a `find(…)` unread instead to see the exact types: Find and aggregation result tabs show the documents exactly as the server sent them.
- In shell syntax (the document editor, the query bar, the dialogs, and a paste that isn't plain JSON), the JavaScript engine moves integer-like keys such as `"10"` ahead of the other keys, in ascending order. Pasted plain JSON keeps them where they are.
- A forgotten master password can't be recovered: Reset is the only way out, and it deletes the saved passwords. The move out of the Keychain happens once, on the first launch of this version on macOS; later launches never read the Keychain.
- The demo server (`--mock`) holds a small made-up shop (`shop`: customers, products, orders) and blog (`blog.posts`), the same at every start, and forgets any change when rongo quits. It supports common query, update and aggregation operators. It reports anything else as unsupported.
- The read-only lock belongs to a connection profile: another profile for the same server is not locked. A write already on its way when you lock a connection still completes.
- Pasting with **Append → overwrite existing `_id`s** replaces each document that is already there with its own round trip (eight at a time; restoring an update does the same), so overwriting a large overlap over a slow connection is slow. Stopping a copy (⊗) waits for the batch in flight; what was written stays, and a collection stopped part-way is left without its indexes (they are copied after the documents).
- Pasting with **Append → overwrite existing `_id`s** into a sharded collection replaces each document by `_id` alone, which MongoDB before 7.1 refuses unless the shard key is in `_id`; that collection then reports an error. Skip, Stop and Replace are not affected.
- Collection History is kept per computer and per connection profile: it can't hold what someone else, another Mac, or another profile for the same server deleted or changed.
- Collection History is encrypted with a key kept in the vault: history files copied to another computer, or kept through a Reset, can't be read or restored (Settings still measures, trims and deletes them).
- With Collection History on, the Delete and Update dialogs (and other filtered deletes and updates) work in batches of 1,000 by `_id` on the documents they saved, rather than as one server-side `deleteMany` / `updateMany`: a document that starts matching while one runs is left alone. A recorded delete goes by the saved `_id`s, so a document someone else changes between rongo reading it and deleting it is still deleted, and its newer version isn't saved.
- Restoring updates on a sharded collection replaces each document by `_id`, which MongoDB before 7.1 refuses unless the shard key is in `_id`.
- With Collection History on, a document over about 8 MB can't be overwritten by Paste → Append → overwrite existing `_id`s (or by a restore): the replace carries the saved version too, to make sure nothing changed it meanwhile, and that passes MongoDB's 16 MB command limit. Paste with history off for that connection, or delete those documents first.
- The Windows installer is not signed, so SmartScreen warns on the first run (More info → Run anyway). The build is for x64; Windows 11 on ARM runs it through emulation. Updates are manual: rongo only tells you a newer version exists (the banner), you run the new installer.
- Not built yet: SQL, an aggregation editor, schema analysis, data compare, and BSON or SQL export.
